# Measurement campaign - plan

One campaign, one commit, raw CSV for everything (formats: `DATA_SCHEMA.md`). Numbers reach the manuscript only through the analysis toolkit (`make_tables.py`, `numbers.tex`). This plan was written before the measurements; the dated sections below record every change made while the campaign ran, and the last section the experiments added on 2026-11-24 and 2026-11-25 (E9, E6x, E4n, E8v).

## Platform, fixed for the whole campaign
- iris = transmitter / initiator (Pi 4 Rev 1.2, 1.5 GHz), baolong = receiver / responder (Pi 4 Rev 1.5, capped at 1.5 GHz with `scaling_max_freq`). Governor `performance` on all cores of both. The boards differ in software: iris runs Debian 13, kernel 6.18.29, GCC 14.2.0, OpenSSL 3.5.5; baolong runs Debian 12, kernel 6.12.47, GCC 12.2.0, OpenSSL 3.0.18. Timings are reported per board; nothing measured on one board stands in for the other.
- eth0 direct cable, 10.10.10.1 / 10.10.10.2, EEE off on both (kernel defect CVE-2026-64125 otherwise stalls iris's receive path), NetworkManager made to ignore eth0, autonegotiation on. Headline speed 100 Mbit/s full duplex (advertise 100baseT/Full only); 1 Gbit/s for the comparison runs named below.
- One tree commit on both boards, Release -O2, liboqs 0.15.0 (final tag) from `~/opt/liboqs-0.15.0`, known-answer tests passed on that build.
- Authentic I-PDU payload 8 bytes for all networked experiments (as the manuscript states); the crypto-only experiment sweeps 8, 64, 256, 1,024 bytes.
- Output goes to `/dev/shm` on the boards and is copied to the Mac after every experiment (iris has about 420 MB of disk left).

## Validity gates (a run that fails one is kept on file but excluded, with the reason)
Recorded before and after every run by `capture_env.sh`: `vcgencmd get_throttled` (must stay `0x0`; the sticky bits show throttling or under-voltage during the run), temperature, governor and frequency of every core, `carrier_changes` and the eth0 address (unchanged), `rbuf_ovflow_cnt` (unchanged), TcpRetransSegs and TCPTimeouts (delta reported; any timeout invalidates a timing run over the link), `--show-eee` (disabled), commit hash and liboqs build (identical on both boards), load average and the five busiest processes before the run (nothing else running), free memory.

## Board discipline during measurement (added 2026-11-23)
- Before a session: `touch ~/array_rev/MEASURING` on every board the experiment uses, wait until `~/array_rev/boardlock.sh status` is free and no compiler, test or rsync process is left, then wait for the idle period. `MEASURING` means no development activity of any kind on that board (builds included). Remove it after the data are copied off.
- Thermal gate: start only below 68 C (`vcgencmd measure_temp`); exclude a run that ends at 78 C or more, or whose `get_throttled` value changed, or that shows a currently-active bit. baolong is rebooted once before the campaign to clear the sticky bit 0x80000 set on 2026-11-23 (builds on all four cores, 80.8 C); after that `get_throttled` must read 0x0 on both boards for the whole campaign. baolong runs hotter than iris (first observation: about 63 C against 62 C at one busy core, 70 C and more with three; the values measured with the real signing loop are in the rulings of 2026-11-23 below): the four-core receiver cells of E7 are run last and their temperature trace is reported.
- One job at a time on a board (added 2026-11-23 08:01): every build, test or run on a board takes that board's lock (`boardlock.sh`) and releases it afterwards; there is no lock-free activity, cores 0 to 2 included. Reason: lock-free builds made a functional loopback run fail (three builds on baolong, 79.8 C) and excluded dry runs through the busy-core gate.
- No SSH session of any kind to a board under measurement (added 2026-11-23 04:45 after an aborted E0 run): the measuring script waits in one blocking session on the board (cpu 0); anyone else tests the LOCAL marker `~/Downloads/pqc-secoc-campaign/MEASURING_<host>` (written by `board_ctl.sh reserve`, removed by `release`) and the `pi` wrapper refuses SSH to a board whose local marker exists (bypass `PI_MEASURER=1` for the measuring script only). No manual status command is run on a board between the start and the end of a measurement.
- Witness for foreign activity (added 2026-11-23): during a session a bash loop pinned to cpu 0 writes the kernel's fork counter every 5 s (`witness_start` / `witness_stop` in `session_lib.sh`, no fork of its own); `own/witness_report.py` lists every 5 s interval with more than 3 new processes; the list is read against the step boundaries in `gates_<host>.txt` (the driver starts processes there) and a burst inside a step is a reason to exclude the step. The E0 session of 04:47 ran without the witness (it was added afterwards).
- Early sessions of E0 and E1 (single-node, they need only `bench_crypto_ops`, cyclictest and the pinned liboqs) may be measured before the integrated tree exists. Such a session counts as a campaign session only if `bench_crypto_ops.c`, `bench_common.h`, the compiler flags and `liboqs.a` (sha256) are byte-identical at the final campaign commit; the harness commit and the file hashes are recorded in the run directory and compared when the campaign commit is fixed. If anything differs, the early session is renamed PILOT. This replaces "one commit" for E0 and E1 only; E2 to E8 are measured at the campaign commit.
- Reserve order (fixed 2026-11-23 08:39 after a deadlock: a job held the lock of baolong and the local marker already refused its SSH, so it could not release): `board_ctl.sh reserve` first creates the marker ON THE BOARD (the lock script then refuses new acquisitions), waits until the holder has released the lock and no build or test is left, and only then writes the local `MEASURING_<host>` file that forbids every SSH session. Nobody but the measuring scripts sets `PI_MEASURER`; it is not set by hand either.
- After a measurement window (added 2026-11-23 08:48): the end of a marker is not a start signal. When `MEASURING_<host>` is removed nobody opens a session by itself; the next holder of the board is named, one at a time (the lock serializes jobs but does not order them).

## Rulings of 2026-11-23
- TCP validity is judged on the experiment's own connection: a timing run over the link is excluded when its own connection retransmitted (`tcp_total_retrans` from TCP_INFO in the harness footer) or when eth0's own counters moved (carrier_changes, rbuf_ovflow_cnt, rx errors). The host-wide TcpRetransSegs and TCPTimeouts are recorded and printed but not judged (they include the SSH sessions over Wi-Fi; they moved during a loopback run on iris). This replaces "any timeout invalidates a timing run" in the validity gates above.
- E0 loaded cells: the signing load runs on ONE other core (cpu 2), not on three. Measured on iris with the real signing loop: one busy core settles at 68 to 69 C; four busy cores reached 81 C in 100 s. The number of sender cores for the multi-core parts of E6 and E7 is fixed after the 2- and 3-core probes; the four-core cells are run only if the boards get better cooling.
- E7: the repetition is the unit of replication (five repetitions per rate step, never pooled); a step is "sustained" only if in every repetition the send queue is not growing and the loss ratio is at most 0.001; the loss ratio is always reported with its exact interval. Ladder rates of a multi-partition run are divisible by the number of partitions. The MAC ladder must go past about 1,000 PDU/s per PDU ID, where the 1 ms main-function cycle (one PDU per PDU ID per cycle in SoAd) and not the HMAC cost bounds the stream; the result names the bound.
- E4: the gateway receiver binary is the oracle (delivered or not, reject stage). The time to the reject decision comes from the gateway only once it carries the harness timestamp hooks; otherwise from a second, labeled run of the same vectors against the harness receiver.
- Processor utilization is never taken from the gateway binary (its main loop polls the clock and uses a full core at any load), only from the harnesses.
- baolong runs at a 1.2 GHz cap during development; `board_ctl.sh reserve` restores 1.5 GHz. Both boards are rebooted before the first session that needs them (iris before E1 session 1).

## Rulings of 2026-11-23 08:35 (after the two-node dry runs; no two-node campaign file exists yet)
- **Retransmissions do not exclude a file (replaces the first ruling above for E6 and E7).** A retransmitted segment makes PDUs late, so excluding a file because its connection retransmitted would select on the outcome and understate the miss ratio. The harness reads TCP_INFO of its own connection at the first release and at the end and writes both; the difference is the number of retransmitted segments of the measured window (the handshake before the first release is not in it). That count, and the kernel's time-out count, are reported per file in the tables; the deadline and delivery figures are computed over ALL valid files, and a sensitivity line gives the same figures over the files without a retransmission. Still invalid: a connection that was re-established inside the window, and the eth0 counters of the first ruling (carrier changes, receive-buffer overflow, receive errors). Reason for the change: in the dry runs two step files had one retransmitted segment each with no late PDU and no time-out, the host-wide counters could not attribute them, and the old rule would have dropped exactly the files in which the transport was slow.
- **TCP no-delay is set (product change, the batch after main 4d95f6f).** Dry runs showed the TcpIp back end never set it: at 1,000 MAC PDU/s about twenty PDUs shared one segment and the receive-minus-send median was 39 ms against 0.79 ms at 500 PDU/s. [SWS_SoAd_00689] item 3 and [ECUC_SoAd_00023] define the path (SoAdSocketTcpNoDelay, `TcpIp_ChangeParameter` with `TCPIP_PARAMID_TCP_NAGLE`). Every file header carries the value read back with `getsockopt`; a timing file whose header does not say 1 on both ends is invalid. A before/after dry run of the MAC ladder must show the median near 1 ms before any campaign run over the link; the frames-per-PDU calibration is redone.
- **Processor time, not board utilization.** `/proc/stat` is tick-sampled on these kernels (CONFIG_TICK_CPU_ACCOUNTING, HZ = 250) and misses work that starts on a timer: in a dry run the sampler showed 0.18 % for a receiver whose process time was 13.4 %. No figure of the paper comes from the `/proc/stat` columns. The sampler gets a column with the cumulative processor time of the measured process (CLOCK_PROCESS_CPUTIME_ID, all threads); the paper reports it as processor time of the process per second and says that kernel network processing outside the process is not included.
- **Negative handshake tests (E4 part): the gateway binary is the judging side on both ends**; the harness supplies the proxy, the driver and the oracle check. Repetitions of tests 1 to 10 come from one rekey trigger and the initiator's own retries; tests 11 and 12 run as repeated short runs. A new gateway option is built only if that cannot work, and then inside the product batch.
- **One product batch, one acceptance.** main 4d95f6f is not accepted: the product tree reopens once (TCP no-delay; the two as-found bound findings in `SecOC.c` if they are found reachable from the wire; nothing else), the test-only follow-ups go into the same head, and the acceptance, the QA gate and the conformance comparison of the touched modules run on that head.

## Rulings of 2026-11-23 09:52 (after the conformance comparison by source inspection, 1,248 catalog rows)
- **The AUTOSAR job model is documented, not built, in this revision.** Finding (blind comparison, confirmed by a search at main: no `ProcessJob` and no `Crypto_JobType` anywhere under `source/` or `include/`): below the SecOC-facing Csm services the port has no job interface (`CryIf_ProcessJob`, `Crypto_ProcessJob`, `Crypto_JobType`); CryIf offers service-specific forwarding functions, the driver is a set of project functions, and the ML-DSA key pair, the peer keys and the session keys are stored in the Csm and reach CryIf as raw bytes (only the MAC keys map by identifier). A job struct that still carries key pointers would change a table row and no property; moving key storage into the driver reopens the handshake, the erasure tests, the mutants and three reviews. Neither fits the one-batch rule. Consequences for the text, binding: every "through Csm, CryIf and a Crypto Driver" statement (abstract, highlights, related-work row, Section 3) is narrowed to "the SecOC-facing Csm service API over project-specific forwarding functions"; E2 / RQ3 measures THIS port's call chain, not the cost of a job-based crypto stack, and says so before E2 is measured.
- **Conformance table of the paper, rule fixed before any status is selected:** one row per module (SecOC, Csm, CryIf, Crypto Driver, SoAd, PduR; TcpIp with its five rows once re-judged), with the number of requirement IDs compared and their counts per status, generated by script from the merged row file; NO selection of individual IDs for the table. Deviations named in the text are those on the path of a Secured I-PDU and the project additions. The caption says: by source inspection against the R25-11 text; follows / simplified / deviates rows were each challenged by a second reader; negative rows outside the sample are one reader's judgment. The row-level list goes into the artifact (`AUTOSAR_CONFORMANCE.md`).
- **Triage of the comparison for defects on the measured path (done before main moves):** SecOC, SoAd and Csm rows called deviates were read for wrong bytes, a PDU wrongly accepted, dropped or duplicated, or a timing effect. Nothing joins the batch. Two points go into the text instead. (1) Overload (corrected 10:02, reading of the code at 6d58d9b, nothing run): the replacement of a queued PDU by its successor does NOT occur while the connection lives. SoAd_MainFunctionTx serves every pending session completely in each call, in request order, one chunk per Secured I-PDU; TcpIp_TcpTransmit does not return before every byte is written, so when the socket cannot take the bytes the one cyclic task waits inside send() (back-pressure), the cycle stretches and a sender with a fixed period falls behind; every PDU that was submitted is sent and confirmed, late. Nothing is dropped by SecOC or SoAd. What becomes of the periods that could not be submitted is the harness's rule (dropped at release, counted). The one place a PDU can be replaced is earlier: two transmit requests for the same row between two calls of SecOC_MainFunctionTx, the second overwrites the Authentic I-PDU of the first ([SWS_SecOC_00110]); it needs an application that submits more than once per cycle per row (to be confirmed: the harness never does, and it calls SoAd_MainFunctionTx once per cycle behind SecOC_MainFunctionTx). No test has two requests for one row inside one cycle. (2) reception is processed in the 1 ms main function, which quantizes the receive path ([SWS_SoAd_00571]).

## Rulings of 2026-11-23 18:02 (before any campaign file of E4 to E7 exists)
- **"Sustained" (E7), made robust:** the send queue of a repetition counts as growing only if the lower bound of the fitted slope times the length of the measured window is at least the size of one Secured I-PDU of the step's profile as it is queued; a smaller growth is "not growing" (a dry run called a 500 PDU/s MAC step not sustained because of one 37-byte sample). The loss criterion is unchanged. The raw slope and its interval stay in the tables.
- **Invalid files:** a file whose footer count differs from its rows, with `rows_lost` other than 0, with `stopped_early=1` or with `contradicting_pdus` other than 0 is invalid with that reason.
- **E6 latency and deadline:** the boards' clocks are not synchronized and the campaign carries no clock-offset file (this holds for E6; experiment E9 of the last section adds a clock probe and a latency across the two boards). The latency of a PDU is the transmitter's release-to-transmit-confirmation time (`response`), and a deadline miss is judged on it against the period; the receiver's verification and delivery times are on its own clock. No cross-board latency is claimed or printed, not even a relative one (the toolkit computes none without a clock-offset file; corrected 18:05 before any E6 file existed).
- **Own readers for E4 to E7** (`own/periodic_compare.py`, `throughput_compare.py`, `attack_compare.py`, `handshake_compare.py`, written independently, from DATA_SCHEMA.md, proven on today's dry-run directories with one negative control each): they recompute the headline quantities only (counts, misses with exact interval and longest run, response percentiles, loss per step, processor time, per-vector counts, handshake times). NOT recomputed by a second reader: the sustained verdict and saturation point, the send queue figures, TCP counters, means and standard deviations, p99.99. Those are the toolkit's alone and the text says nothing about them that the own readers do not cover, except the sustained rate, which is quoted with its rule.

## Sessions
A session is a fresh set of process launches after both boards have been idle for five minutes. Experiments whose tail behavior differed between May and November (E1 signing tail, E6 at 10 ms) are run in at least three sessions and reported per session, never pooled. Order of configurations inside a session is randomized with a recorded seed.

E1a, which run supplies which statement (written 2026-11-23 08:17, while the plain campaign run was being measured and before any campaign file of E1a had been copied or read; the two dry runs of 06:20 and 06:21 with 20,000 calls each had been read, they validated the tool and are not results):
- The plain run (`E1a_s1_iris_*`, no counting) supplies everything that is a time of an uninstrumented signing call: wall time against thread CPU time per call, the floor of their difference, the number of calls whose wall time exceeds a threshold and how many of them also have a CPU time above it, the time off the processor.
- The counting run (`E1ac_s1_iris_*`, `COUNT_SHAKE=1`) is an instrumented run. It may supply: the number of rounds per call (mean, share of one-round calls, largest), the relation between CPU time and rounds as measured in that run (intercept, time per round, residuals, R²), the number of rounds at which the fitted line crosses a threshold, the share of calls with at least that many rounds with its exact interval, and the 2×2 count of CPU time above a threshold against rounds at or above the crossing. Each such statement is labeled in the text as coming from the instrumented run, and the median signing time of the counting run is printed next to that of the plain run so that the reader sees what the counting costs.
- The counting run may not supply: any latency percentile, mean or maximum of the signing time, any exceedance share of the signing time quoted as the paper's deadline figure (those come from the three E1 sessions, Table of exceedances), or a time off the processor.
- The geometric share computed from the measured one-round share is a model value, printed as such next to the measured share; it is never printed alone.
- If the counting run's median signing time differs from the plain run's by more than 1 %, the time-per-round figure is stated as that of the instrumented build only and the crossing round is not carried over to the uninstrumented timing without that caveat.

Method of the isolated-core repeat (decided 2026-11-23 under the label E9; the repeat was not run): the boot files of the boards are not edited (rule: nothing that existed on the boards before this revision is modified). The isolated core is made at run time and is gone after a reboot: a cgroup v2 cpuset partition of type `isolated` holding cpu 3 (removes the core from the scheduler's load balancing, the run-time equivalent of `isolcpus=domain`), movable interrupts steered to cpus 0 to 2 through `/proc/irq/*/smp_affinity`, the measured process started inside that cpuset. `nohz_full` cannot be had without a boot parameter and is named as not applied. If the cpuset controller is not available on the board's kernel, E9 is dropped and the text says so. Checked on iris 2026-11-23: `/sys/fs/cgroup/cgroup.controllers` lists `cpuset cpu io pids`, so the method is available there.
