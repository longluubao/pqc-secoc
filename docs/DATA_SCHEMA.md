# Run directory and CSV schema (contract between harnesses and analysis)

One run = one directory `runs/<run_id>/` with:

```
env_<host>.txt        hostname, board model, kernel, gcc, liboqs version+build flags, governor, cur/max freq,
                      temperature and vcgencmd get_throttled before and after, git commit hash, link speed, clock sync state
<experiment>/*.csv    raw data, schemas below (header row mandatory, times in nanoseconds, CLOCK_MONOTONIC of the writing host)
<experiment>/cmd.txt  exact command lines used
MANIFEST.sha256
```

All CSVs: comma-separated, one header row, no units in values, no blank lines. Lines starting with `#` are comments (anywhere in the file, including after the data) and must be ignored by row parsers; harness files carry `# key=value` metadata there (top: tool, commit, compile flags, liboqs version, pinned CPU, governor, start frequency, mlockall status; bottom: end frequency, CPU time over wall time, context switches and, for paired files, `signature_mismatches` and `failed_calls`). A harness file without its bottom block was interrupted and is invalid.

Markers in a run directory: a file `DRY_RUN` or `PILOT` means nothing in the directory may be quoted as a result; the analysis then marks every generated number visibly. Validity (a run is excluded from results, with the reason recorded): non-zero `signature_mismatches` or `failed_calls`; `mlockall` not ok; start and end frequency differ; CPU time over wall time clearly below 1 for a pinned single-thread run; `vcgencmd get_throttled` in `env_<host>.txt` showing a currently-active bit, or a value after the run that differs from the value before it. Temperature is recorded before and after; a run on a board that starts at 68 C or more is not started, and one that ends at 78 C or more is excluded (baolong reached 80.8 C and flag 0x80000 on 2026-11-23 while several builds ran on it). The process list and the busy jiffies of the other cores are recorded after the run as well as before: another busy process during the run excludes it.

## crypto_ops.csv - single-node primitive timing
`op,seq,ns`
- `op` ∈ `mldsa_keygen, mldsa_sign, mldsa_verify, mlkem_keygen, mlkem_encaps, mlkem_decaps, hkdf, hmac_gen, hmac_verify`
- `seq` starts at 0 per op; analysis drops `seq < warmup` (default 1000).

## overhead_paired.csv - standalone vs Csm-integrated, paired and interleaved
`seq,order,op,standalone_ns,csm_ns`
- Both paths process the **same message with the same signing randomness** in pair `seq`; `order` ∈ `AB, BA` says which ran first (randomized per pair), where **A = standalone, B = Csm-integrated**. `op` ∈ `sign, verify`.
- The harness does not discard warm-up; analysis drops `seq < 1000`.

## periodic_tx.csv / periodic_rx.csv - periodic streams, deadline analysis
Tx: `stream,seq,release_ns,start_ns,auth_done_ns,send_done_ns`
Rx: `stream,seq,rx_done_ns,verify_done_ns,deliver_ns,result`
- `stream` is the stream index 0..K-1 (not the PDU identifier); the Tx header line `# stream_pdu_ids=<id>,<id>,...` maps each index to its SecOC PDU. `# rep=<k>` and `# partitions=<N>` are written into every periodic and throughput file.
- `release_ns` is the nominal periodic release instant (open loop: releases never wait for the previous job).
- **Every released job gets exactly one row**, including jobs that were dropped or still unfinished when the run ended: stages a job did not reach are written as `0`, and such a job counts as a deadline miss. `seq` is contiguous per stream starting at 0.
- A job misses its deadline when `send_done_ns - release_ns > deadline` (deadline = period unless stated).
- Mandatory comment block at the top of the Tx file, one `# key=value` per line, exactly these keys: `period_ns`, `deadline_ns`, `streams`, `cores` (number of CPU cores the sender may use), `profile` (`mldsa65` or `mac`), `scheduler` (`other`, `fifo`, `fifo_isolated`), `payload_bytes`, `commit` (git hash), `host`.
- Optional Tx header keys, recorded when the harness supports them: `mainfunction` (`cyclic` or `event`), `mf_period_us`, `phase` (`sync` or `staggered`), `partition` (index of the gateway process in a multi-core run).
- Optional key in either file: `not_recorded=<column>[,<column>]`. The writing binary has no timestamp for that stage (the gateway application before the BSW timestamp hooks are integrated): the column is `0` in every row, the stage is reported as not recorded, and those zeros are NOT missed stages. Without this key a `0` keeps its meaning (stage not reached, deadline miss).
- `result` ∈ `ok, freshness_fail, auth_fail, framing_fail`.
- For `framing_fail` rows the receiver cannot attribute the bytes to a PDU: `stream` and `seq` are written as `-1`, and such rows are counted per run, never matched to a transmitted job.
- Rx stage semantics: `rx_done_ns` = complete Secured I-PDU reassembled (for `framing_fail`: the instant the framing error was detected); `verify_done_ns` = instant of the accept/reject decision (after the freshness check for `freshness_fail`, after the authenticator check for `auth_fail` and `ok`; `0` for `framing_fail`); `deliver_ns` = handed to the application, `0` unless `result` is `ok`. Verification time = `verify_done_ns − rx_done_ns`, delivery time = `deliver_ns − rx_done_ns`, both reported over `ok` rows; the reject-decision time is reported per failure class.

## throughput.csv - sustained load, sampled once per second on each host
`t_ns,host,offered_pps,pdus_done,cpu_busy_jiffies,cpu_total_jiffies,if_tx_bytes,if_tx_packets,if_rx_bytes,if_rx_packets,sendq_bytes,drops`
- Mandatory comment block at the top: `# tx_host=<hostname>`, `# rx_host=<hostname>`, `# profile=`, `# cores=`, `# commit=`. One file per host per offered rate step (rate steps are not mixed in one file).
- `pdus_done` is cumulative (sent on Tx host, delivered on Rx host). `cpu_*` are cumulative sums over the pinned core(s) from `/proc/stat`. `if_*` are cumulative eth0 counters from `/sys/class/net/eth0/statistics`. `sendq_bytes` is the TCP send-queue depth (`SIOCOUTQ`) at the sample instant; 0 on the Rx host. `drops` is cumulative PDUs the generator could not enqueue or the receiver rejected.

## attack.csv - on-the-wire attack injection (receiver side)
`vector,iter,delivered,reject_stage,detect_ns`
- `vector` ∈ `benign, replay, bitflip, auth_tamper, freshness_rollback, session_replay`; `delivered` ∈ 0/1 (1 = reached the application); `reject_stage` ∈ `none, framing, freshness, auth`; `detect_ns` = time from complete reception to the reject decision.
- `session_replay` (added 2026-11-23 08:47, before any campaign attack file exists): a Secured I-PDU recorded in an earlier session is injected in a later session of the same two gateways. Expected: not delivered, `reject_stage` = `auth` (the authenticator of both variants is bound to the session; tests C13 and C16 of the tree show it in process). The row's `iter` counts the injected PDUs; the run directory names the session identifiers of the recording and of the injection.

Header line `# oracle=`: `gateway_app_log` (the gateway receiver binary decides delivered or not and the reject stage; it records no instant of the decision, so `detect_ns` is 0 in every row and means "not recorded": no detection-time number is derived from such a file) or `harness` (the harness receiver with its timestamp hooks; `detect_ns` is the time from reception to the reject decision). A file without the line is treated as `harness`. Added 2026-11-23.

## handshake.csv - authenticated ML-KEM handshake
`seq,role,result,total_ns,bytes_tx,bytes_rx,keygen_ns,encaps_ns,decaps_ns,sign_ns,verify_ns,kdf_ns,hash_ns,mac_ns`
- One row per attempt on each host, failures and dropped M1 included; `seq` is the per-host attempt index from 0. `role` ∈ `initiator, responder`; unused timing fields are 0.
- `result` ∈ `ok, bad_ver, bad_len, unknown_id, sig_fail, mac_fail, timeout, state`.
- `total_ns` on the writing host's CLOCK_MONOTONIC: initiator = from the start of ML-KEM key generation to keys installed (after M3 is handed to SoAd; the later M4 is not included); responder = from M1 completely received to keys installed after M3, or to abort. The responder's total includes the initiator's computation and two network legs; totals include main-function scheduling and are not crypto time; per-role compute = sum of the stage columns (`hash_ns` = all transcript hashes, `mac_ns` = key-confirmation HMAC generate and verify).
- `bytes_tx` / `bytes_rx` count message bytes including the 8-byte SoAd PDU header of each message.
- Comment keys at the top: `# mainfunction=event` or `# mainfunction=cyclic`, `# mf_period_us=`, `# t_min_ms=` (the minimum handshake interval in force), plus the usual tool, commit, host lines.

## clock_offset.csv - cross-host clock relation (only if one-way latency is reported)
`t_ns,offset_ns,rtt_ns,method`
- `offset_ns` = receiver clock − transmitter clock (signed), `t_ns` on the receiver's clock, `rtt_ns` the round-trip time of the exchange the estimate came from, `method` a short label (for example `ptp4l-sw`, `udp-ping`). The file sits in the same directory as `periodic_rx.csv`. Without it no cross-host latency is reported.

## sign_attrib.csv: attribution of the signing tail (E1a, added 2026-11-23, bench commit cdf8175)
`seq,wall_ns,cpu_ns`, one row per ML-DSA-65 signing call of `bench_sign_attrib` (same call and set-up as `mldsa_sign` in crypto_ops.csv), `seq` contiguous from 0; `wall_ns` is CLOCK_MONOTONIC and `cpu_ns` CLOCK_THREAD_CPUTIME_ID around the same call, read in the order monotonic, thread CPU, sign, thread CPU, monotonic, so `wall_ns >= cpu_ns - 2000` in every row and `wall_ns - cpu_ns` is the time the pinned thread did not run.
Header keys as crypto_ops.csv plus `clock_order`, `cpu_clock`, `cpu_timer_overhead_ns`; footer and validity rules as crypto_ops.csv; file `crypto_attrib/sign_attrib_p<payload>.csv`. Warm-up: `seq` < 1000 dropped, as in crypto_ops.csv.
Reading rule: whether interrupt handling counts as "did not run" depends on the kernel option CONFIG_IRQ_TIME_ACCOUNTING (with it, interrupt time is taken out of the thread's CPU time; without it, interrupt time is charged to the interrupted thread and appears as CPU time). The run record states the option of the board's kernel, and the text may say "descheduled" only for what the option makes it mean. The two reads of the thread CPU clock are system calls inside the wall interval (about 1.2 us per call), so `wall_ns` of this file is that much longer than in crypto_ops.csv.
Floor of `wall_ns - cpu_ns` (found on the first real files): the two reads of the thread CPU clock lie inside the wall interval and outside the CPU interval, so every call shows a few microseconds of difference that were spent on the processor (median 5.5 us on baolong). The plain sum of the differences is therefore NOT a time off the processor. Time off the processor is read as (a) the footer's `wall_s - cpu_s` for the whole file, (b) the difference above the floor (the median), summed over the calls more than 100 us above it, (c) the counts of calls with a difference above 100 us, 1 ms, 5 ms.
With `--count-shake` (bench commit 780ef25; an instrumented run of its own: the latency tables of the paper never take a number from it; quantities that need the count, such as the processor time per round, are reported as coming from the instrumented run): a fourth column `shake_calls`, the number of SHAKE-256 state initializations inside the call, and the header keys `shake_counted`, `shake_calls_min`, `shake_calls_step`, `shake_probes`; rounds of the rejection loop = (shake_calls - shake_calls_min) / shake_calls_step + 1. Without the switch the header carries `shake_counted=off` and the file has three columns. How the count is taken: liboqs's public hook `OQS_SHA3_set_callbacks` with a copy of liboqs's own table in which one entry counts and forwards; the table that is copied (`sha3_default_callbacks`) is a symbol of liboqs.a that no installed header declares. liboqs is neither changed nor rebuilt; the text states that this run is instrumented.

## Handshake keys in the networked harness files (added 2026-11-23; final at the integrated head)
`periodic_tx*.csv` and `periodic_rx*.csv` carry the header lines `# handshake=` (the protocol label `PQC-SecOC-HS-v1`, or `off` for a session-less run), `# session_id=` (the 4-byte session identifier in hex; equal on both ends of a run, otherwise the run is EXCLUDED), `# hs_installs=` and `# hs_established=`. The harness writes `handshake_tx*.csv` / `handshake_rx*.csv` with the columns of handshake.csv and the comment keys `mainfunction`, `mf_period_us`, `t_min_ms`, `t_pend_ms`, `t_a_ms`, `t_flush_ms`, `session_id`. The driver compares the session identifiers of the two ends of every run (against a gateway: with the gateway's installation line and its own handshake.csv) and writes `sessions.txt`. A timing run of the campaign releases no PDU before the handshake attempt has ended with `ok` and the session is established; a failed attempt ends the transmitter with exit 5 and nothing released.

## Transport keys of the networked harness files (added 2026-11-23 08:53, rulings of 2026-11-23 08:35 of CAMPAIGN.md; before any two-node campaign file exists)

Header of `periodic_tx*.csv` and `periodic_rx*.csv` (and of every other networked timing file):
- `# tcp_nodelay=` : TCP_NODELAY read back with `getsockopt` on the harness's own connection: 1, 0, or -1 if the call failed. Transmitter: read at the instant of the first TCP_INFO snapshot (between `established_ns` and `first_release_ns`); receiver: once the session is established, before the first PDU. **A networked timing file whose value is not 1, or which lacks the key, is invalid; a periodic pair (transmitter and receiver file of one stream and run) is invalid as a pair when either end fails, since one connection has one configuration (clarified 2026-11-23 09:00).** A ladder file or `attack.csv` that does not carry the key itself is judged by the header and footer of the traffic log beside it (never by its rows); no such log, or one of another host, repetition or partition, makes the file invalid. An `attack.csv` of either oracle is invalid as a whole unless the value is 1 (the join script writes `tcp_nodelay`, `tcp_nodelay_tx`, `tcp_nodelay_rx`; with the gateway as oracle the receiving end is taken from the gateway's own `# tcp_nodelay=` lines; -1 means an end has no read-back).

Footer of `periodic_tx*.csv` (the transmitter's connection; the receiver's connection carries only acknowledgements and handshake messages and gets none of these). Two snapshots of `getsockopt(TCP_INFO)`: one in the 200 ms between `established_ns` and `first_release_ns`, one at the end after the send queue has drained.
- counters, each at both instants and as their difference (`_in_window` = the measured window; the handshake before the first release is not in it): `tcp_total_retrans_at_first_release`, `tcp_total_retrans_at_end`, `tcp_total_retrans_in_window` (retransmitted segments); `tcp_dsack_dups_*` (duplicate-SACK reports received: the peer already had the segment); `tcp_total_rto_*` (retransmission time-outs; needs a kernel header of 6.7 or later).
- gauges, at both instants, no difference: `tcp_lost_*` (segments now marked lost), `tcp_retrans_*` (segments now retransmitted and unacknowledged), `tcp_rto_us_*`, `tcp_rtt_us_*`.
- -1 means the kernel or the board's header did not give the field; it is never written as 0.
- `tcp_total_retrans` (whole connection, read at the end) stays, so earlier files remain readable; it is not judged.
- `tcp_connections_at_first_release`, `tcp_connections_at_end`: number of `connect()` calls the stack has made in this process (counted by the harness's wrap, independent of the product code; attempts are counted, so the value at the first release can be 2 when the first attempt found no listener). **A file in which they differ is invalid** (the connection was made again inside the window).
- **A file is NOT invalid because of retransmissions.** The driver writes `NOTE_tcp_retrans` with the three window counts per file; the analysis reports the counts. Throughput: per rate step the figures over all valid repetitions and, as a sensitivity line, over the repetitions whose transmitter files all have `tcp_total_retrans_in_window` = 0 (with the number left out; an unknown count, -1, counts as not 0). Periodic: the count is a column of the tables; no figure is pooled across configurations; a second figure exists only where several files already form one (the combined miss ratio of a multi-partition cell).
- Per board and step, host-wide and not judged (they include other connections of the host): TcpExtTCPLossProbes, TCPLossProbeRecovery, TCPTimeouts, TCPFastRetrans, TCPSlowStartRetrans, TcpRetransSegs before and after the step, in the gate snapshot.

Sampler files `throughput_tx*.csv`, `throughput_rx*.csv`: one more column at the end, `proc_cpu_ns`.
- `proc_cpu_ns`: CLOCK_PROCESS_CPUTIME_ID of the harness process at the sampling instant, cumulative nanoseconds, all threads of the process (worker, sampler, main). Processor time of the process over an interval = difference of two samples; divided by the difference of their `t_ns` it is the share of one core. It is the processor time of the process, NOT board utilization: work the kernel does in other contexts is not in it; interrupt time that interrupts the process is charged to it on these kernels (CONFIG_IRQ_TIME_ACCOUNTING not set, see `env_<host>.txt`). With N partitions each file is its own process.
- The `/proc/stat` columns (`cpu_busy_jiffies`, `cpu_total_jiffies`) stay; they feed the counter-consistency guard only. No figure of the paper comes from them (tick-based accounting misses work that starts on a timer).

## Jobs given up, and what "loss" means in a ladder (added 2026-11-23 10:04, before any two-node campaign file exists)
- Footer of the transmitter's files: `jobs_released`, `jobs_dropped_at_release`, `jobs_started`, `jobs_confirmed`, `tx_confirmations_ok`, `tx_confirmations_failed`; sampler column `drops` = dropped at release plus given up.
- **A networked timing file is invalid when `jobs_started` differs from `jobs_confirmed`** (a job was given up without a confirmation after 2,000 ticks in cyclic mode or four cycles in event mode; the row then received its next PDU).
- The harness releases at the nominal instants T0 + j x period per stream; each release enters the stream's queue of at most `backlog_jobs` jobs (default 4) and is dropped there and then when the queue is full (`jobs_dropped_at_release`; the job keeps its row with `release_ns` and zeros in the other columns). A row of SecOC gets its next PDU only after SoAd confirmed the previous one.
- By the code of the stack (reading of 6d58d9b: SoAd serves every pending session completely in each call; TcpIp waits in send() until every byte is written) nothing is dropped inside SecOC or SoAd under overload. **Loss of a ladder (corrected 10:18; the quantity itself is unchanged):** the loss ratio is (offered - delivered) / offered inside the window, with offered = sent + dropped at release on the transmitter and delivered counted on the receiver. It is an end-to-end figure: releases dropped at a full queue, plus PDUs sent and not yet delivered when the window ends, plus anything the receiver did not deliver. The sustained verdict keeps this figure as its input (CAMPAIGN.md). Next to it the tables give the share of releases dropped at a full queue inside the same window, taken from the transmitter's sampler column `drops` (corrected 12:15: not from the footer, whose count includes the ramp; and it is NOT a part of the loss ratio: the PDUs not delivered net those in flight at both ends of the window, the drops are counted on the transmitter alone, so the two figures stand side by side and neither bounds the other). The text describes the loss as "not delivered inside the window", never as PDUs lost by the stack or by the network.
- `jobs_started` = `jobs_confirmed` is judged in `periodic_tx*.csv` and, for a ladder's sampler file, an `attack.csv` and a handshake-negative run, in the traffic log beside it; missing lines in a harness-written transmitter file make the file invalid (not recorded).
- Handshake files: the header key `pdu_stream` says what ran beside the handshakes (`none` for E5; `periodic` and so on for the set-up handshake of another experiment). A handshake file with `pdu_stream` other than `none`, or with a `periodic_tx*.csv` / `periodic_rx*.csv` beside it, or below a `throughput*`, `attack*` or `calibration*` directory, is a set-up handshake: listed, not analyzed. The handshake files of the negative tests (`hstest/handshake_gw_tx.csv`, `handshake_gw_rx.csv`, written by the gateway binaries) give counts per result class and side as keys and no timing statistic; the oracle's verdict per test is read from the driver's record.

## Record of a negative handshake test (added 2026-11-23 10:41; oracle self-test 23 checks; no campaign file exists yet)
`hsneg.txt` of a negative-test run: lines for a reader, then exactly ONE line that starts with `test=`, then `PASS` or `REJECT` as the last line. The one line, fields separated by one blank, in this order:

`test=<1..12> variant=<none|drop|sig|mac|key|flip> repetitions=<n> attacked=<n> verdict=<PASS|FAIL> expected_tx=<list> seen_tx=<list> expected_rx=<list> seen_rx=<list> repetitions_done=<n> runs=<n> runs_passed=<n> pdus_sent=<n> pdus_delivered=<n> pdus_rejected=<n> pdus_given_up=<n> installs_tx=<n> installs_rx=<n> tcp_nodelay_tx=<1|0|-1> tcp_nodelay_rx=<1|0|-1>`

- tx is the initiator, rx the responder; the counts come from the two ends' own handshake files (the gateways' files when gateway binaries run on both ends).
- `<list>` is `result:count` joined by commas, only the classes that occur, in the order ok, bad_ver, bad_len, unknown_id, sig_fail, mac_fail, timeout, state; `none` if empty.
- `repetitions` = asked; `attacked` = handshakes the proxy edited, messages it injected, or probes sent (tests 9, 10); `repetitions_done` = complete repetitions found.
- `expected_*` = the rows of the first handshake plus those of the complete repetitions found; `seen_*` = all rows of that side. They may differ by the rows of one unfinished repetition at the end of a run (PASS allows exactly that, with `state` as the row a closing connection leaves).
- `variant`: test 11 has drop, sig, mac, key; test 12 has drop, flip; the others `none`.
- A batch (tests 11 and 12: runs r001.. under one lock) gives one line for the whole batch: `runs` = number of runs, counts summed over the runs, verdict PASS only when every run passed; each run's own line is in `hstest/rNNN/hsneg.txt`.
- `pdus_given_up` > 0 makes the verdict FAIL; `tcp_nodelay_*` other than 1 on an end makes it FAIL.
- Header key `pdu_stream` of handshake files: `none` is written by the E5 tools only; known edge: the harness receiver also writes `none` for a failed periodic run in which no PDU arrived.

## Functional runs of the gateway binaries (E3) in the toolkit (ruled 12:15, before any campaign run of that kind)
A run directory written by the gateway driver (marker `FUNCTIONAL`; files `app_tx*.csv`, `app_rx*.csv`, `rx_payload*.csv`, `handshake_tx*.csv`, `handshake_rx*.csv`) goes through `make_tables` as a functional experiment: counts only (PDUs sent per stream, delivered, delivered in order and byte-exact, rejected per result class, handshakes per result class and side, TCP connections with their `tcp_nodelay` read-back), never a timing statistic. A handshake file in such a directory is counted, not timed. The campaign scripts' `accept_check.py` stays the independent reader of the same directories.
- (added 12:51) Attack directories are NOT functional runs in this sense: there the join script's `attack.csv` is the analyzed file, and the gateway's logs are its source. A `tcp_nodelay` read-back other than 1 on any connection of a functional run makes the run invalid (as the driver's checker and `accept_check.py --require-nodelay` do). A directory with the marker and no `app_tx*` / `app_rx*` file (build and link steps) is listed as incomplete, not analyzed. A run in which no session comes about (wrong peer key) is a result with zeros, not an incomplete run. Parts of a replaced process are added in numeric order; the driver's `*_all.csv` files are not read. Delivered in order = per stream, the delivered sequence matched in order against the sent sequence; byte-exact = the payload of a delivered PDU has the pattern of its stream and sequence number, judged against the TRANSMITTER's rows. The columns of `app_tx*.csv`, `app_rx*.csv`, `rx_payload*.csv`, the payload pattern, the restart of sequence numbers with a new transmitter process, the sequence number of a rejected row and the meaning of the header key `count` are defined by the gateway's code and are copied here in the next section.

## Contract of the gateway's application logs (functional runs; from the code at main 9f22628, copied here 2026-11-23 12:55)
All of it is functional evidence: the gateway's sender is closed loop, so no rate, deadline or latency may be computed from these files. Every timestamp is CLOCK_MONOTONIC of the writing host in ns; values of the two boards are not comparable. "stream" is the index of the stream in the variant of the run (mldsa65: signature PDU i; mac: MAC PDU i; both: stream 0 = signature PDU 0, stream 1 = MAC PDU 0), not a PDU ID.
- Files: `app_tx.csv` (transmitting gateway), `app_rx.csv` and `rx_payload.csv` (receiving gateway), `handshake_tx.csv` / `handshake_rx.csv` (the handshake application of each gateway). A replaced process writes files with the suffix 2; the driver's joined `*_all.csv` (first part whole, then the data rows and tcp_nodelay lines of the second) carry the header keys of the FIRST process only and are not to be read by the toolkit. Files are line buffered (rows survive a kill).
- `app_tx*.csv`: `stream,seq,submit_ns,start_ns,auth_done_ns,send_done_ns`, one row per PDU, written when its transmission is CONFIRMED with E_OK (an unconfirmed PDU has no row). `seq` from 0 per stream and per process; `submit_ns` first release; `start_ns` directly before the last SecOC_TpTransmit call (differs from submit_ns only after a re-submission after 2,000 cycles without confirmation; the PDU keeps its seq); `auth_done_ns` always 0 (not recorded); `send_done_ns` instant of the transmit confirmation (SoAd handed the last byte to TCP).
- `app_rx*.csv`: `stream,seq,rx_done_ns,verify_done_ns,deliver_ns,result`, one row per outcome; `result` is one of ok, freshness_fail, auth_fail, framing_fail. ok: stream from the PDU ID of the Com notification, seq decoded from the LAST four bytes of the delivered payload, rx_done_ns 0 (not recorded), verify_done_ns = instant of the success status, deliver_ns = instant of the Com notification. freshness_fail / auth_fail: stream from the Data ID of the status, seq -1, verify_done_ns = instant of the status call-out, deliver_ns 0. framing_fail: stream -1, seq -1, rx_done_ns = instant the application READ SoAd's drop counter (not the arrival).
- `rx_payload*.csv`: `stream,seq,payload_hex`, one row per delivered PDU in the order of the ok rows; the delivered Authentic I-PDU as Com handed it over, lower-case hex.
- `handshake_*.csv`: `seq,role,result,total_ns,bytes_tx,bytes_rx,keygen_ns,encaps_ns,decaps_ns,sign_ns,verify_ns,kdf_ns,hash_ns,mac_ns`, one row per entry the handshake component hands out: an attempt that ended, OR a message discarded without ending one. `seq` is a row index per process (not an attempt counter); `role` initiator or responder; `result` one of ok, bad_ver, bad_len, unknown_id, sig_fail, mac_fail, timeout, state. `total_ns`: initiator from the start of ML-KEM key generation to keys installed (M3 handed to SoAd; M4 not included) or to the abort; responder from M1 completely received to keys installed or the abort; a discarded message from completely received to the decision. bytes include the 8-byte PDU header per message. Functional record only: handshake timing of the paper comes from the bench harness.
- Header keys: app_tx: loop=closed, commit, host, role=tx, profile, streams, payload_len, period_cycles (BSW cycles of 1 ms between two releases of a stream), count, not_recorded=auth_done_ns. app_rx: commit, role=rx, profile, count, not_recorded=rx_done_ns. rx_payload: commit, role=rx, profile, count. No host key in the two receiver files. handshake: tool=SecOC gateway, commit, host, mainfunction=cyclic, mf_period_us, t_min_ms. `commit` is the build stamp, the same in all five files of a run.
- `count`: in app_tx the PDUs to be confirmed on EACH stream before the process exits (in a replaced transmitter: RESTART_AFTER in the first process, the rest in the second). In a receiver file it is NOT a number of PDUs sent: it is the number of outcomes of any kind after which the receiver exits (count x streams + forged + tampered copies; RESTART_AFTER for the first receiver of a restart run; 0 = no limit for the receiver that replaces it). Not usable to judge completeness.
- **Payload of an Authentic I-PDU (corrected):** 8 bytes for every stream: byte 0 = stream index, bytes 1 to 3 = 0, bytes 4 to 7 = the sequence number, 32 bit, big endian. The pattern is defined for a payload of 8 bytes only.
- A new transmitter process starts every stream at 0 again (two numbering runs in a restart-tx run).
- Which row for which rejection: a PDU that SoAd drops before SecOC sees it gives ONE framing_fail row per counted drop (unknown header ID, length outside the route's limits, StartOfReception refused, a connection that ends inside a PDU or with unparsed bytes, and so on; no stream and no time of arrival known). freshness_fail = the no-session gate, or a counter not above the last accepted one. auth_fail = everything else that is not a success: a wrong authenticator, a Secured I-PDU that does not fit its layout, a Csm answer other than success, the retries for a busy Csm used up: i.e. "verification failed or could not be done", not only "wrong signature". A header byte above the Authentic I-PDU maximum gives framing_fail or auth_fail, one of the two, never both. **A PDU of a row that is not a stream of the run's variant writes NO row at all** (in a mac run a forged signature PDU leaves no trace in app_rx.csv). The transmitter writes no row for an unconfirmed PDU and releases nothing before a session exists.
- `# tcp_nodelay=<0|1>` lines: comment lines BEHIND the column line (the header keys are written before a connection exists), one per TCP connection of the process (when first seen, and again for each connection that replaces it); the value is TCP_NODELAY read back from the connected socket. A reader must skip `#` lines anywhere and collect ALL values. No line = no TCP connection was ever seen by that process, or the read failed. Seen so far: 1 line per file in a plain run; 2 in the receiver's three files when an injector connected first or the transmitter was replaced; 2 in the transmitter's two files when the receiver was replaced.

## clock_probe.csv: clock relation of the two boards (E9; tool bench_clock_probe)

Written by the probe client on board A (the transmitter's board) after it is told to end (SIGTERM or SIGINT): it first completes the window of 5 s that is running then (windows are counted from its first completed exchange; up to 5 s more), so that the last anchor is the best exchange of a whole window, and then writes `periodic/clock_probe.csv` of a harness run, `clock_probe.csv` beside the application logs of a functional run. A client that was killed otherwise leaves an empty file.

- Header, one `# key=value` line each: `tool=bench_clock_probe`; `commit` (first 12 hex digits of the harness commit; `-dirty` is appended when the tree the driver ran from had uncommitted or untracked files); `host_a` (client; t1 and t4 are on its clock); `host_b` (server; t2 and t3 are on its clock); `clock=CLOCK_MONOTONIC`; `interval_ms` (101 in the campaign: not a multiple of the 10 ms release period, so that the exchanges do not meet every release at the same phase); `port` (UDP port of the server); `cpu_a`, `cpu_b` (the core each process is pinned to; -1 not pinned).
- Columns `seq,t1_ns,t2_ns,t3_ns,t4_ns`, integer nanoseconds: t1 read on A immediately before the request is sent, t2 on B immediately after the request was read, t3 on B immediately before the reply is sent, t4 on A immediately after the reply was read.
- Rows: one per completed exchange, in the order sent. Request k is due at the start plus k times the interval; `seq` counts the requests from 0. An exchange without its reply within 0.9 of the interval after it was due, or whose send failed, is lost and shows as a gap in `seq`; a reply that comes later is ignored. Every row has t1 <= t4, t2 <= t3 and (t4 - t1) - (t3 - t2) >= 0.
- Footer: `exchanges_sent`, `exchanges_completed` (equal to the number of rows).
- How the offset track, the bound and the end-to-end keys are computed, and when a run is not a result for E9: E9_SPEC.md, "Interface details", the rulings, and above all "FINAL ruling on the clock track" with its addition, which supersede the earlier forms.
- The driver starts the probe 12 s before the first release and stops it 12 to 17 s after the last delivery (12 s of lead plus the completion of the last window).

## e9_check.txt: the harness's own verdict on the clock track of a run (E9)

In the run directory, written by `check_clock_probe.py` of the harness commit after the run. Free-text lines (exchanges, anchors, delay, largest gap; the region from the second to the second-to-last anchor; exchanges outside the track; distance of the region's ends from the first release and the last delivery; PDUs joined and causality; latency minimum, median, maximum as a plausibility line, not a result), then ONE last line: `PASS` or `FAIL`, followed by the tokens `offset_bound_us=` (largest delta/2 over the anchors of the region), `offset_cert_us=` (the smallest T such that the exchanges certified to within T, with the region's ends, leave no gap above 2,000 ms), `offset_bound_total_us=` (the larger of the two; limit 100) and `exchanges_outside=` (exchanges of the region further from the track than their own delta/2 plus the total bound); a FAIL line continues with `; <reason>` per failed rule. A FAIL leaves the marker `E9_INVALID` in the run directory and driver status 1; the periodic files of such a run are complete and valid for the deadline analysis, only the end-to-end latency is not a result. The published keys come from the analysis toolkit and are compared with the own reader (`own/e2e_compare.py`), not from this file.

## Probe format 2 (E9 on the raw clocks; harness commits after b42716bc3e8c)

The section above describes probe format 1 (first pass of E9, CLOCK_MONOTONIC stamps only; those files are kept as measured and not used for latency). The latency campaign uses format 2 (E9_SPEC.md, Addendum E with its readings E11 and its amendment E12). Three files lie side by side (`periodic/` of a harness run, beside the application logs of a gateway run):

- `clock_probe.csv`, written by the probe client on board A as before. Header as in format 1 plus `# format=2` (second line) and `# clock_raw=CLOCK_MONOTONIC_RAW`. Columns `seq,t1_ns,t2_ns,t3_ns,t4_ns,t1r_ns,t2r_ns,t3r_ns,t4r_ns,w1_ns,w2_ns,w3_ns,w4_ns`. At each of the four stamp points the probe reads CLOCK_MONOTONIC_RAW, CLOCK_MONOTONIC, CLOCK_MONOTONIC_RAW with nothing in between: `tN_ns` is the monotonic read (meaning and position as in format 1), `tNr_ns` the raw stamp of the exchange (before a send, points 1 and 3, the SECOND raw read; after a receive, points 2 and 4, the FIRST), `wN_ns` the distance between the two raw reads of the point; the other raw read is the stamp minus the width at points 1 and 3 and plus the width at points 2 and 4. Rows and footer as in format 1. The request datagram is as long as the reply (100 bytes each).
- `clock_map_a.csv` (written by the client, board A) and `clock_map_b.csv` (written by the server, board B, when it is told to end): the relation between the two clocks of that board, sampled by a second thread of the probe process every 5 ms from the start of the process to its end. Header: `# tool=bench_clock_probe`, `# commit=`, `# host=`, `# role=a|b`, `# clock=CLOCK_MONOTONIC`, `# clock_raw=CLOCK_MONOTONIC_RAW`, `# interval_ms=5`, `# cpu=`. Columns `raw1_ns,mono_ns,raw2_ns`: one sample is three reads in that order. Footer `# samples=<rows>`, `# samples_dropped=<samples that found the memory full>`. A sample is valid when 0 <= raw2 - raw1 <= 5,000 ns; its value is mono - (raw1 + raw2) / 2. A run of 1,000 s gives about 206,000 samples per board (about 10 MB).
- Every file is written under `<name>.tmp` and renamed when complete, so a file that exists is complete; a probe that was killed leaves none.
- How the stamps of the PDUs (CLOCK_MONOTONIC of each board, unchanged) are carried onto the raw clock of their board with these maps, how the offset between the boards is tracked on the raw stamps, which bounds are computed and when a run is not a result for E9: E9_SPEC.md, Addendum E (E3 to E5), the readings E11 a to o and the amendment E12 (the kink term of the map bound, the identity of the three files).
- `e9_check.txt` of a format-2 run: the lines of the harness checker (raw track; widths of the exchange points; each map: samples, not valid, dropped, widths, late samples, used range, largest gap, hold-out, kink term, half-width, bound, check points; the bound in total; coverage; causality; latency minimum, median and maximum as a plausibility line; one diagnostic line with what the format-1 definitions make of the monotonic columns), then ONE last line `PASS` or `FAIL` with the tokens `offset_bound_us=`, `offset_cert_us=`, `offset_bound_total_us=` (the raw track), `map_bound_a_us=`, `map_bound_b_us=`, `bound_total_us=` (the sum of the three, limit 100) and `exchanges_outside=`; a FAIL line continues with `; <reason>` per failed rule and prints `none` for a bound that could not be computed.
- `check.txt` of a harness run carries one line per probe file (`<path>: ok` or `<path>: <fault>`), written by the driver from the probe checker's verdict on format, footers and counts, behind the lines of the schema check of the other CSV files.
- Keys: E9_SPEC.md, E10 (the earlier key names now refer to the raw values; new: `bound_total_us`, `probe_format`, `probe_width_p50_ns`, `probe_width_max_ns`, per board `map_X.*` with `map_X.kink_us`, and `clock_X.adj_*`, which say how the board's CLOCK_MONOTONIC moved against its raw clock during the run).

## Profile both in the periodic files (E9, cell h)

`periodic_tx.csv` and `periodic_rx.csv` with `# profile=both`: stream 0 is the signature stream and stream 1 the MAC stream, in both files; `# streams=2` (transmitter); `# stream_pdu_ids=2,13`; `# stream_header_ids=0x10,0x20`; `# stream_profiles=mldsa65,mac`, one entry per stream index, written in this profile only (in the profiles mldsa65 and mac every stream has the file's profile). Rows as before, both streams in the one file under their stream index; `releases_per_stream` holds for each. Both streams are released at the same instants and handed to SecOC in the same cycle, stream 0 first.

## background_traffic.txt: the unrelated flow of a periodic run (E9, cell i)

In the run directory, written by the driver from the two ends' own files (`periodic/bg_source.txt`, `periodic/bg_sink.txt`). `key=value` lines: `rate_offered_bit_s`; `rate_achieved_bit_s` (bytes sent times 8 over the source's duration); `pattern` and `seed` (how the writes are spaced: the mean rate is fixed, the gaps between writes are random between 0.5 and 1.5 ms from the seed, so that the flow does not meet every release at the same phase); `bytes_sent`; `bytes_received`; `writes`; `max_deficit_bytes` (the most bytes the source was behind its nominal count when it came to write: one gap's worth, about 9 kB at 50 Mbit/s, when nothing holds it up; a larger value means the source was held up at that moment); `send_timeouts` (writes that a full send buffer held up for 0.5 s; recorded, not judged); `source_duration_ns`, `sink_duration_ns` (first to last byte at that end); `source_host`, `sink_host`; `source_cpu`, `sink_cpu`; `source_first_byte_ns`, `source_last_byte_ns` (CLOCK_MONOTONIC of board A, comparable with `release_ns` and `send_done_ns`); `sink_first_byte_ns`, `sink_last_byte_ns` (board B); `source_ended_by`, `sink_ended_by` (signal, connection or limit); last line `verdict=PASS` or `verdict=FAIL: <reasons>`. FAIL: achieved below 95 % of offered; nothing received or more received than sent; the flow began after the first release or ended before the last `send_done_ns`. A FAIL leaves `BG_INVALID` and driver status 1.

## Files and lists of the further cells of Addendum H (E3r, E6m, E6p; added 2026-11-26, after the runs; formats as the drivers at 02b340b03679 and 524cf0902eea write them)

- **`# phase=` in `periodic_tx.csv`** (harness commit 524cf0902eea): `sync` (the default, also where the line is absent) releases all streams of a sender process at the same instants; `staggered` releases stream s of the k streams of the process s/k of a period after stream 0, in every period (driver variable `PHASE`, option `--phase staggered` of `bench_net_tx`). The spacing is even, not random. The deadline of a job is judged from its own release in both cases. The cell name inside a key ends in `-sync-part<i>` or `-staggered-part<i>`.
- **Several sender processes on one core (E6m).** One pair of files `periodic_tx_p<i>.csv` / `periodic_rx_p<i>.csv` per sender process, as in the cells with two processes; `# cpu_affinity=` of every sender file names the same core. The toolkit then writes cell-level keys under `<config>-parts<N>`: releases and misses added over the processes, `cores` as the number of distinct cores, and `auth_utilisation` as the time covered by the union of the intervals from `start_ns` to `auth_done_ns` of all processes over the time from the first release to the last transmit confirmation. The per-process timing keys of such a cell (`auth_*`, `service_*`, `response_*`) contain the time in which the other processes held the core and are not signing times.
- **A gateway process replaced during a functional run (E3r; gateway driver `scripts/run_e2e.sh`, variables `RESTART=tx|rx`, `RESTART_AFTER`).** The replaced process ends after `RESTART_AFTER` PDUs per stream (sender) or outcomes (receiver), and a second process of the same role is started; the files of the second process carry the suffix 2 (`app_tx2.csv`, `handshake_tx2.csv`; `app_rx2.csv`, `rx_payload2.csv`, `handshake_rx2.csv`, and the logs `tx2_<host>.log`, `rx2_<host>.log`), and `<name>_all.csv` is the driver's concatenation of the two, which its checker reads. The toolkit adds the handshake rows of a role over its files; `functional.lost` is sent minus delivered in order. A PDU that reaches the second receiver before its session exists is logged by it as `freshness_fail` with sequence number -1.
- **A new session key on request (`REKEY_AT`)**: the sender asks for a second handshake after that many PDUs of stream 0; both `handshake_tx.csv` and `handshake_rx.csv` then hold two rows.
- **`keyrepl_pubkey_sha256.txt`** (run `E3r_s1_sig_keyrepl_*` only): two lines, `before=<sha256>` and `after=<sha256>`, the checksum of the public key file of board A's gateway before its two key files were removed and after the run had made a new pair. Written into the run directory by the campaign script after the driver had written the directory's `MANIFEST.sha256`, so that manifest does not list it; the manifest at the top of the dataset does.
- **Lists of runs** (tab-separated; a line that begins with `#` is a comment). `e9_tries.tsv` and `cells2_tries.tsv`: run identifier, key prefix, status, reason; status `result` (the run is in `accepted_runs.tsv`), `not_a_result` (measured or started and not accepted; the reason says why), and in `cells2_tries.tsv` also `not_run` (a cell that was not run in the window: the first field is empty and no run directory exists). `e9_not_started.tsv`: run identifier and reason, for identifiers of the latency campaign under which no measurement was started. `runs_not_used.tsv`: run identifier, key prefix, the accepted run of the same cell, reason, for a valid run of a cell that already had its result (the first valid run of a cell is its result).
